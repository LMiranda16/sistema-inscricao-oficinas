# Sistema de Inscricao em Oficinas

Uma API REST feita com Spring Boot para consultar, cadastrar e remover participantes, oficinas e inscricoes. O projeto usa Java 21, Maven e PostgreSQL.

> Feito para organizar oficinas sem perder o historico das inscricoes. Bora! :-)

## O que a API faz?

- Lista e consulta por ID participantes, oficinas e inscricoes.
- Cadastra participantes, oficinas e inscricoes.
- Remove participantes e oficinas quando nao ha inscricoes relacionadas.
- Cancela inscricoes preservando o historico e devolvendo a vaga a oficina.

## Tecnologias

- Java 21
- Spring Boot 4.1.2
- Spring Web MVC
- Spring JDBC (`JdbcTemplate`), fornecido pelas dependencias Spring Boot
- Spring Session JDBC (dependencia presente; nao ha funcionalidade de sessao exposta pela API)
- PostgreSQL
- JUnit Jupiter, Mockito e Spring MVC Test (testes)
- Maven Wrapper

## Pre-requisitos

1. JDK 21 instalado.
2. PostgreSQL acessivel pela aplicacao.
3. As tabelas `participantes`, `oficinas` e `inscricoes` criadas no banco.

Confira se o Java esta instalado:

```text
java -version
```

Se `JAVA_HOME` ainda nao estiver definido, configure-o para a pasta onde o JDK 21 foi instalado.

Linux/macOS:

```sh
export JAVA_HOME="/caminho/para/jdk-21"
export PATH="$JAVA_HOME/bin:$PATH"
```

Windows CMD:

```bat
set "JAVA_HOME=C:\Program Files\Java\jdk-21"
set "PATH=%JAVA_HOME%\bin;%PATH%"
```

O caminho varia conforme a instalacao. Confirme com `java -version`.

Crie as tabelas no PostgreSQL antes de iniciar a aplicacao:
```sql
CREATE TABLE participantes (
   id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
   nome VARCHAR(120) NOT NULL CHECK (LENGTH(TRIM(nome)) > 0),
   email VARCHAR(150) NOT NULL UNIQUE
);

CREATE TABLE oficinas (
   id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
   titulo VARCHAR(150) NOT NULL CHECK (LENGTH(TRIM(titulo)) > 0),
   capacidade INTEGER NOT NULL CHECK (capacidade > 0),
   vagas_disponiveis INTEGER NOT NULL,
   CONSTRAINT vagas_validas CHECK (
       vagas_disponiveis >= 0
       AND vagas_disponiveis <= capacidade
   )
);

CREATE TABLE inscricoes (
   id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
   participante_id BIGINT NOT NULL
       REFERENCES participantes(id) ON DELETE RESTRICT,
   oficina_id BIGINT NOT NULL
       REFERENCES oficinas(id) ON DELETE RESTRICT,
   data_registro TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
   situacao VARCHAR(15) NOT NULL DEFAULT 'ATIVA'
       CHECK (situacao IN ('ATIVA', 'CANCELADA'))
);
```

## Rotas

Todas as rotas usam o prefixo `/api`.

| Metodo | Rota | Descricao |
| --- | --- | --- |
| `GET` | `/api/participantes` | Lista todos os participantes. |
| `GET` | `/api/participantes/ordenar` | Lista participantes por ID crescente. |
| `GET` | `/api/participantes/{id}` | Busca um participante pelo ID. |
| `POST` | `/api/participantes` | Cadastra um participante (`nome`, `email`). |
| `DELETE` | `/api/participantes/{id}` | Remove um participante sem inscricoes relacionadas. |
| `GET` | `/api/oficinas` | Lista todas as oficinas. |
| `GET` | `/api/oficinas/ordenar` | Lista oficinas por ID crescente. |
| `GET` | `/api/oficinas/{id}` | Busca uma oficina pelo ID. |
| `POST` | `/api/oficinas` | Cadastra uma oficina (`titulo`, `capacidade`); as vagas iniciam iguais a capacidade. |
| `PUT` | `/api/oficinas/{id}` | Atualiza titulo e capacidade; capacidade nao muda se houver historico. |
| `DELETE` | `/api/oficinas/{id}` | Remove uma oficina sem inscricoes relacionadas. |
| `GET` | `/api/inscricoes` | Lista o historico de inscricoes. |
| `GET` | `/api/inscricoes/ordenar` | Lista inscricoes por ID crescente. |
| `GET` | `/api/inscricoes/{id}` | Busca uma inscricao pelo ID. |
| `POST` | `/api/inscricoes` | Inscreve participante em oficina e consome uma vaga. |
| `DELETE` | `/api/inscricoes/{id}` | Cancela uma inscricao ativa, preserva o historico e devolve a vaga. |

Criacoes retornam `201 Created`, buscas retornam `200 OK`, exclusoes de participantes/oficinas retornam `204 No Content` e o cancelamento de inscricao retorna o registro atualizado com `200 OK`. Dados invalidos retornam `400 Bad Request`, recursos inexistentes `404 Not Found` e conflitos (por exemplo, e-mail duplicado, inscricao ja cancelada, oficina lotada ou exclusao bloqueada por inscricoes) `409 Conflict`.

Para criar uma inscricao, envie `POST /api/inscricoes` com os IDs de um participante e de uma oficina existentes:

```http
POST /api/inscricoes
Content-Type: application/json

{
 "participante_id": 1,
 "oficina_id": 1
}
```

O participante e a oficina precisam existir, e a oficina precisa ter vagas disponiveis. A resposta `201 Created` inclui a inscricao criada.

Exemplos de requisicoes HTTP com `curl`:

```sh
curl http://localhost:8080/api/oficinas
curl http://localhost:8080/api/participantes
curl http://localhost:8080/api/inscricoes
curl http://localhost:8080/api/oficinas/ordenar
curl http://localhost:8080/api/oficinas/1

curl -X POST http://localhost:8080/api/participantes -H "Content-Type: application/json" -d "{\"nome\":\"Ana\",\"email\":\"ana@example.com\"}"
curl -X POST http://localhost:8080/api/oficinas -H "Content-Type: application/json" -d "{\"titulo\":\"Programacao\",\"capacidade\":20}"
curl -X POST http://localhost:8080/api/inscricoes -H "Content-Type: application/json" -d "{\"participante_id\":1,\"oficina_id\":1}"

curl -X DELETE http://localhost:8080/api/participantes/1
curl -X DELETE http://localhost:8080/api/oficinas/1
curl -X DELETE http://localhost:8080/api/inscricoes/1
```

Os exemplos com `curl` podem ser executados em Linux, macOS e Windows quando o `curl` estiver instalado.

Para manter as vagas consistentes, criar uma inscricao e consumir sua vaga, assim como cancelar uma inscricao e devolver a vaga, sao operacoes transacionais. A exclusao de participante ou oficina referenciada por inscricoes e rejeitada pelo banco.

## Algoritmos em memoria

A classe `utils.Oficina` oferece busca linear por ID, que percorre a lista elemento a elemento, e busca binaria por ID, que divide a busca em uma lista ja ordenada. O metodo `ordenarPorId` usa Bubble Sort para ordenar em ordem crescente; a lista deve ser ordenada antes de chamar a busca binaria. As rotas `/ordenar` usam o Bubble Sort por ID. As consultas por ID da API usam SQL, nao as buscas em memoria.

## Refatoracao e testes

As tres listagens ordenadas repetiam a criacao de uma copia e a chamada ao Bubble Sort. Essa logica foi reunida no metodo `ordenarPorId` do business process. O teste `ordenaAsTresEntidadesPorIdCrescenteSemAlterarAsListasDoRepository` verifica a ordem das tres listagens e que as listas originais nao sao modificadas. O teste `rejeitaInscricaoAtivaDuplicada` verifica a regra de duplicidade. Os testes com mocks nao comprovam transacoes reais nem concorrencia no PostgreSQL.

## Arquitetura

```text
controller -> businessprocess -> repository -> PostgreSQL
```

- `controller`: rotas HTTP e formatos das requisicoes.
- `businessprocess`: regras de negocio e coordenacao das transacoes.
- `repository`: consultas SQL e acesso ao banco com `JdbcTemplate`.
- `controller` chama somente `businessprocess`; somente `repository` acessa o banco.
